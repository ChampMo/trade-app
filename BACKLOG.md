## Phase 1 — engine + risk (weeks 2–3)

- [x] P1-01 Config & profiles. Done 2026-09-02: `Profile` = demo | paper | live, each with its own journal (`data/journal-<profile>.db`) and port (8001/8001/8002, overridable via `API_PORT`); `ALLOW_LIVE` on a non-live profile is now a load-time error, and `live_enabled` is the single value handed to the broker guard. The "two cores side by side" half of the check needs the API, so it is verified under P1-09.
- [x] P1-01b MT5 startup diagnostics. Done 2026-09-03 with P4-01: `connect()` retries the busy terminal (-10003/-10005) with a backoff and **nothing else** — a wrong password or the wrong server fails identically on attempt two, and repeated logins are how broker accounts get locked (D22). A terminal that is running but logged out is caught by `terminal_info().connected` on every tick, not only at startup. Both paths have tests in `tests/test_watchdog.py`.
- [x] P1-02 Strategy runtime. Done 2026-09-03: plugins live in `src/tradeapp/strategies/` and register with a decorator, so adding one is adding one file. A strategy that raises is disabled on the spot with a CRIT event and a traceback, and so is one that returns an Intent for the wrong symbol or the wrong type; the others carry on. Variants of the same strategy run side by side for A/B (D9). Deviation from the original wording: the runtime is **synchronous and owns no event loop**, because building asyncio tasks before there is a loop to run them in would be speculative. It is called from a loop in live and from a for-loop in backtest, which is rule 04 in practice; the async wrapper lands with P1-10.
- [x] P1-03 Context v0. Done 2026-09-03: `Context` is the only thing a strategy sees — bars, indicators, tick, symbol info and the AI view — with no broker, no balance and no way to place an order. Indicators (`indicators.py`) follow MT5's definitions: EMA seeded with an SMA, Wilder smoothing for ATR and RSI, and `None` during warm-up so a half-formed value can never be traded on. Values are cached per (indicator, period). `MT5Broker.bars()` drops the still-forming bar by default, since strategies decide on closed bars. Verified end to end on live XM H4 bars with `python -m tradeapp signals`.
- [x] P1-04 Risk Engine v0. Done 2026-09-03: 17 named rejection reasons, each with its own test; sizing from equity × risk_pct × confidence × AI size_mult × bias penalty, lots always rounded **down**; daily loss, drawdown, max positions, max open risk, per-currency netting, trading hours, news hook, duplicate-position and stop-distance checks. Every call writes a `decisions` row, approved or rejected, with the context that produced it. `python -m tradeapp risk` previews a decision against live prices without sending anything; verified on XM demo (0.12 lots / $24 on a $10k account, and the stop-too-close and size-below-minimum rejections both fire correctly against XM's real 20-point spread). Rule 02 is now enforced structurally by `tests/test_rule_02_single_door.py`.
- [x] P1-04b Risk Engine follow-ups. Done 2026-09-03 (D23): **free margin** — the engine asks the terminal's own `order_calc_margin` what an order would tie up and falls back to arithmetic when it cannot answer; a single order may use at most 25% of free margin. Verified against XM demo, where the broker said 13.92 USD for 0.12 lots and our fallback said 13.9154. It is nowhere near binding at 1:1000, which is the point: a live account with lower leverage should refuse rather than let the broker reject, because three rejections in a row trip the kill switch. **Correlation** — a coarse signed table in `risk/correlation.py` counts how many copies of the same bet would be open (the new trade is 1.0, a 0.85-correlated position adds 0.85, a hedge subtracts) and refuses past 2.0. It may only ever refuse, never size up, and an unknown pair counts as uncorrelated because inventing a correlation is worse than missing one. **Per-strategy budgets** — 1.5% of equity of realised loss a day and 0.5% of open risk, so an account that is still healthy can stop the one strategy that is not. The daily number comes from the journal's own fills, read only on bars that actually have signals. 23 tests.
- [x] P1-05 Kill switch. Done 2026-09-03: 7 numeric triggers (D12a), each with a fault-injection test; on trigger it locks the state first, closes everything with retries, then **re-reads positions from the broker** and reports `complete=False` if anything is left, or "positions unknown" if the terminal cannot be read at all. A notifier that raises is swallowed so Telegram being down never leaves positions open. `unlock(reason)` requires a non-empty reason and lands in PAUSED; `resume()` is a separate deliberate step. `python -m tradeapp drill` fires all of it and journals the result: 12/12 passing. The kill switch is the only module besides the bridge and smoke allowed to reach the broker, and `tests/test_rule_02_single_door.py` restricts it to `close_position` — an emergency brake that can also open positions is not a brake.
- [x] P1-05b Kill switch fully wired. Done 2026-09-03 with the core loop: every tick builds a `SystemHealth` from the executor's counters and reconcile's findings and calls `check_and_trip` before anything can open; reconcile runs on its own timer. `test_the_full_kill_unlock_resume_cycle` drives RUNNING → KILLED → PAUSED → RUNNING through the loop. Fixed a real bug found by that test: the switch used to re-evaluate while PAUSED, so it slammed shut again on the tick right after an unlock and the operator could never get back in. It now only fires while RUNNING.
- [x] P1-06 Execution layer. Done 2026-09-03: `execution.py` sends an approved `OrderRequest`, retries only the retcodes that mean "never reached the book" (requote, price changed, price off, rate limit) and **never** a TIMEOUT, since that is ambiguous and a retry could open the position twice. Slippage is signed from the trader's point of view and journaled on both the open and the close. Rule 03 verification moved here out of `smoke.py`, so the smoke test now proves the exact code live trading runs. It also produces `consecutive_rejects` and `last_broker_contact_utc` for the kill switch. 22 tests, including retry exhaustion, a raising broker, and the decision-to-order journal link.
- [x] P1-07 Paper execution. Done 2026-09-03: `broker/paper.py` wraps a real broker for everything that reads and simulates everything that writes, so no order leaves the machine. Unlike the backtest broker it cannot see the future — stops and targets are checked against the ticks that actually arrive, and a gap past a stop fills where the market was. `--paper` on `run` and `serve`. A test drives the whole Core loop through it and asserts the wrapped broker was never asked to trade.
- [x] P1-08 Reconcile. Done 2026-09-03: `reconcile.py` compares broker positions against what the ledger believes, derived from the orders table rather than kept as state. The two directions are treated differently on purpose (D17): an **orphan** freezes new entries and becomes a kill-switch mismatch, a **ghost** is a stop doing its job and is recorded as `CLOSED_ELSEWHERE` without an alarm. Also audits rule 03 and feeds `positions_without_stop`. A broker that cannot be read freezes rather than assuming nothing is open. Positions outside our magic numbers are reported and never acted on. 16 tests; `python -m tradeapp reconcile` runs it against the live account, and the core loop now runs it on a 60-second timer.
- [x] P1-09 Core API. Done 2026-09-03: FastAPI on localhost with status, positions, events, decisions, orders, strategies, ticks, the four control endpoints and a WebSocket that walks the journal forward by id (no pub/sub layer — the journal is already the truth). The loop runs in a background thread behind one lock in `service.py`, and a loop that raises journals CRIT and stops loudly rather than dying quietly. `serve` refuses any non-loopback host: there is no auth and `/control/kill` is one POST away. 19 tests.
- [x] P1-10 Core as a background process. Done 2026-09-03: `scripts/start-core.cmd` plus docs/RUNNING.md with the Task Scheduler setup, the machine settings that matter (no sleep, updates outside market hours, Algo Trading re-enabled after every account change) and what does and does not survive a restart. **[owner]** still to do: create the scheduled task on this PC and confirm it comes back after a reboot.

## Phase 2 — backtest, UI, first two strategies (weeks 3–5)

- [x] P2-01 Historical data cache. Done 2026-09-03: `data.py` is a plain SQLite store, not parquet — the project has stayed dependency-light and the file opens in DB Browser like the journal does, which matters when a backtest looks wrong. Upsert by (symbol, timeframe, time), so re-syncing overlaps is free and a broker revising its history overwrites rather than duplicates. Gap detection knows the FX weekend is the market being shut, not missing data. Verified: pulled 20,000 real EURUSD H4 bars from XM covering 2013-10 to 2026-09; the only 21 gaps it reports are Christmas and New Year.
- [x] P2-02 Backtest engine. Done 2026-09-03: `BacktestBroker` implements the same `Broker` surface as the MT5 bridge, so `run_backtest` drives the **real** Core loop, Risk Engine, Executor and StrategyRuntime rather than a parallel simulation — rule 04 taken seriously. Costs: per-bar spread (with a news multiplier), commission, swap and slippage, and the spread cost is tracked separately because it never shows up as a line item. A bar that could have hit both stop and target is scored as the stop; OHLC cannot say which came first and the optimistic reading is how losing systems get published as winners. The kill switch stays live during a backtest. Toy strategies reproduce hand-computed PnL to the cent.
- [x] P2-03 Walk-forward and Monte Carlo. Done 2026-09-03: `robustness.py`. Walk-forward fits each training window across a parameter grid and measures the winner on the untouched window that follows; the efficiency ratio is total out-of-sample over total in-sample, which is harder to game than a mean of ratios. Monte Carlo reshuffles the same trades because every ordering was equally possible, and reports p50/p95/p99 drawdown — the p95 is the number to size against, not the one run that happened. `gate_report` collects exactly what D3 and P2-05 check.
- [x] P2-04 Two strategies that disagree. Done 2026-09-03: `ema_cross` (H4 trend) and `meanrev_m15` (M15 fade back to the average). Deliberately opposite ideas, since two variations of one idea would tell us nothing about netting or about a combined equity curve. Both backtest end to end on real XM data and **both fail their gates** — see docs/RESEARCH.md. The A/B/C variant split needs the calendar and the AI layer, so it lands with P3-04. Next: filter meanrev to fewer, better signals rather than more of them.
- [x] P2-05 Strategy lifecycle. Done 2026-09-03: `lifecycle.py` holds D3's numbers as gates with no force parameter; `promote` refuses and names every unmet condition. A parameter change demotes back to research, because ninety untouched days only mean something if nothing was touched. Verified against the real thing: promoting `ema_cross` is refused with `profit factor: need > 1.0, have 0.769`. 31 tests.
- [x] P2-06 UI shell. Done 2026-09-03: Vite + React + Tailwind in `ui/`, wrapped by Electron. Top bar with the mode badge, state, equity, both risk gauges and KILL; Dashboard, Strategies (with the lifecycle ladder), Journal browser and Events. Verified against a running core: the KILL dialog demands a reason **and** the word KILL, the red banner appears on every page, unlock demands a reason and lands in PAUSED, and the whole cycle is visible in the Events page afterwards. The websocket streams live. Electron holds no trading logic and no credentials — closing the window never stops the bot (D7).
- [x] P2-07 Research and Risk pages. Done 2026-09-03: the core gained six research endpoints and a worker that runs **one backtest at a time** — a replay is minutes of CPU on the same machine as the loop that is trading, so the request answers immediately with a job to poll and a second launch is refused with a 409. A failed job is a recorded status, never an exception near the core. The Research page runs one, watches it, lists every stored run and opens one for its statistics, costs, Monte Carlo and gates, with a button that compares it against live. The Risk page is **read-only and says why**: a limit is a decision in DECISIONS.md, and there is no write route behind the page at all, which has its own test. Verified end to end in a browser against a running core: launched a 19,900-bar ema_cross replay from the button, watched the job finish, and read the same -442.04 the command line reports. 23 tests. **Fixed on the way**: the API sent journal timestamps as naive ISO strings, so every browser read them as local time and the UI showed every journal row seven hours out under a column headed UTC.

## Phase 3 — AI layer (weeks 5–7)

- [x] P3-01 Economic calendar and news blocking. Done 2026-09-03: `calendar.py`, and there is no model anywhere in it — a release time is known days ahead, so nothing needs predicting. SQLite store with upsert-by-event, a parser that understands both this project's shape and the common ForexFactory weekly JSON, and skips one malformed row rather than losing the whole feed. `NewsWindows` implements the `NewsBlocker` protocol the Risk Engine already accepted, so wiring it in changed no decision code. Defaults are HIGH impact and ±30 min (D3): blocking on every number would stop trading most of the day and teach you to switch it off. **No default feed URL on purpose** — which calendar to trust is the owner's decision, and a wrong one silently either stops the bot or lets it trade through NFP. 26 tests.
- [x] P3-02 DeepSeek client. Done 2026-09-03: one POST over httpx, no SDK, so changing provider is a change to one file. Daily spend is tracked in the journal and survives a restart; past the cap the client stops answering and the system trades on rules. Every call stores the raw prompt and reply in `ai_calls` so a year of decisions can be replayed later. Strict Pydantic bounds — a reply outside them is a parse failure, and a parse failure keeps the previous view rather than retrying until the model says something acceptable. **The prompt carries no account data**: no balance, no positions, no tickets, and a test asserts it. Verified with a real call on the owner's key: it returned regime `downtrend`, bias −0.4, size ×0.8, for $0.00018.
- [x] P3-03 Agents. **Analyst** done 2026-09-03 — the only one that can change a trade — and wired into the loop: asked once per closed bar, because that is the only moment its answer can matter. Every failure path (no key, budget spent, network down, bad schema) keeps the previous view, and an expired view collapses to neutral by itself. **Scout and Reviewer** done 2026-09-03 (D24), and both are defined by what they cannot do. The Scout **never writes to the calendar** and its prompt forbids stating a time or a date: a model will give you a release time and it will sometimes be wrong, and the calendar is the thing that stops the bot trading through NFP. It writes a briefing that expires after 36 hours, filtered to the traded pair's own currencies, which the Analyst reads under a label saying it is unverified. The **Reviewer** comments on a day and is told in the prompt that the deterministic classification is not up for debate; its opinion is stored beside that answer, never instead of it, and it may not propose a parameter change (D11). Neither prompt carries account data. 19 tests, and the scout verified against the real API: ten items on EUR/USD, no invented times. Aggregation stays plain code.
- [~] P3-04 A/B comparison. `python -m tradeapp report ab` groups closed trades by strategy and variant using the magic numbers (D9), and prints the table. What is still missing is the wiring that runs three variants side by side with the calendar and AI flags set differently — the runtime already supports variants, but nothing registers them that way yet.
- [x] P3-05 No key, still trading. Done 2026-09-03: `test_removing_the_key_leaves_a_working_system` pulls the key and asserts the Risk Engine still approves a normally-sized trade. `--ai` is opt-in, so the default run has no AI in it at all.

## Phase 4 — hardening + forward test (weeks 7–10)

- [x] P4-01 Watchdog + auto-reconnect. Done 2026-09-03: every tick asks the terminal whether it is still attached to the broker — `terminal_info().connected`, not our own flag, because MT5 will happily hold a live process that has lost the broker. A dropped terminal is shut down and reattached on the spot, the server clock is re-measured (a reconnect can land on the other side of a DST change, D13), and every reconnect is a WARN in the journal and a number on the dashboard. While the terminal is unreachable the loop **opens nothing** — every limit is computed from the position list, and acting on a stale one is worse than missing a bar — and if the silence passes 60s the kill switch trips; a kill that cannot reach the broker says CANNOT REACH THE BROKER rather than claiming success. `python -m tradeapp drill` now runs 16 drills in two groups, four of them taking the terminal away mid-run, and one of those drives the real bridge rather than a fake broker. 13 tests. **[owner]** still to do: close MT5 while `serve` is running and confirm the reconnect in the journal (RUNNING.md); that is gate 5 in D3 and no simulated drill substitutes for it.
- [x] P4-02 Telegram. Done 2026-09-03: CRIT out immediately, WARNs batched so an hour of reconnect noise is one message, heartbeat every 15 minutes so **silence is the alarm**. Nothing outbound can raise — the kill switch calls it, and a dead notifier must not stop a close. Inbound is the dangerous half and every update is checked against the configured chat id, because anyone who learns the bot's name can message it; that one comparison is the whole authentication story and it has its own test. `/status` and `/kill` work from a phone; **`/unlock` deliberately does not**, since coming back from an emergency needs the journal and a phone in a pocket is not that. 22 tests. `python -m tradeapp notify test` proves the channel before you need it. **[owner]** still to do: run that once and confirm the message arrives, then `serve --telegram` and try `/kill` on demo.
- [x] P4-03 Daily post-mortem. Done 2026-09-03: `reports.py` stitches order rows back into round trips and classifies losses. Only **execution** and **bug** can lead to a code change; **variance** is just the record. **`regime` is never assigned automatically**, on purpose — it needs judgement across weeks, and a rule that guessed would quietly relabel ordinary losing streaks as regime changes, which is the exact mistake the classification exists to prevent (D11). The report proposes nothing and says so. Verified on the real journal: it found the day's four smoke trades and correctly called all of them variance. **[owner]** still to do: schedule `report postmortem --write` nightly.
- [x] P4-04 Weekly drift report. Done 2026-09-03: backtests are now stored in the journal (`backtests`, schema 3) — stats, costs, walk-forward, Monte Carlo, gates and every closed trade, but not the equity curve, which is one point per bar and no comparison uses it. `report drift` then measures a live period against a stored run in **points per trade**, never money: lot sizes differ between a backtest on a flat 10,000 and a live account that has moved, and comparing money would call that drift. Six metrics with thresholds (win rate 10 points below, expectancy halved or turned negative, trade count or hold time off by half), and a refusal to conclude anything under 20 live trades — a strategy that wins a third of the time shows 0% for its first five trades, and a report that called that drift would get a working strategy changed for no reason (D11). Slippage is reported separately because unlike the rest it is actionable. 14 tests. Every backtest run is saved by default; `--no-save` opts out.
